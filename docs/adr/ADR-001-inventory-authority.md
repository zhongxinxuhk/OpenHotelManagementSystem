# ADR-001：实体资源事实与可重建日历

> 2026-10-19；S0-04；状态：继承实体房权威原则，物理映射为实施候选，待业务冻结与数据库验证。

## 背景

原架构以 reservation_room 为实体占用事实，日历是派生数据；状态机新增 L/S/G 后，需要避免混淆购买需求、计划资源和实际使用。维修若处于另一个互斥域，还会产生交叉冲突。

## 决定

1. 将预订 A 与维修 B 的日期互斥事实统一映射到 `room_occupancy`，用 kind 区分；原 reservation_room、room_block 名称仅保留概念对应，不同时维护两套可写事实。
2. L 表达一间销售需求；A 表达实体房和日期；S/G 表达实际履约。当前 A 按有效状态查询，部分唯一兜底；至少一个和联合状态由事务核对。
3. 资源/日期变更采用后继 A，保留旧区间、前驱、变更操作和原因。正常状态迁移仍更新当前 A 并写审计；不删除历史以释放库存。
4. 日历仅服务当前/未来查询，按房间锁及 availability_version 重建；不以事件 UUID/序列最大值推断提交水位，不以历史流水累计归零作为退房完成判据。
5. 真实未分房配额是独立方案。DEC-05 未确定前只能按实体分配分支设计，不能通过 A.room_id 可空绕过实体保障。

## 备选与影响

保留 reservation_room 与 room_block 两张事实表并使用统一行锁也是可实现路线，但要求所有写路径都遵守跨表协议。本稿选统一表，使日期冲突有直接数据库兜底；代价是 kind/引用/状态组合 CHECK 更复杂，正式迁移和领域访问必须明确过滤类别。

不采用“只保存日历数字”或“Redis 剩余数为真相”，它们不能表达整段同房承诺和实际入住历史。分段换房不能自动当作连续可售房。

## 验收与替代条件

执行 DM-03—DM-06、DM-14—DM-17、DM-28/29；历史保留、净差流水、并发重建和连续房可用均需实际数据证据。若 DEC-05/16 改变资源或时间粒度，先补配额/小时/床位模型并重新估算，不向当前表塞空值规避约束。
