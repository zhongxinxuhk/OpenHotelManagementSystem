# ADR-019：三条身份平面的会话隔离与实名人工审核

- 状态：已接受（2026-11-01）
- 决策人：需求方（2026-11-01 明确两条约束）+ 本项目
- 关联：[ADR-016](./ADR-016-authn-authz-tenant-isolation.md)（认证与租户隔离）、
  [ADR-017](./ADR-017-multi-surface-and-identity-planes.md)（多端与身份平面）、
  [ADR-018](./ADR-018-guest-identity-and-verification.md)（住客身份与实名）

## 1. 背景与两条需求约束

需求方在 2026-11-01 对开放问题给出两条定论：

1. **住客会话不复用员工会话**，"角色完全隔离，杜绝越权"；
2. 实名核验走"**权威接口 + 人工审核**"双通道：权威接口熔断时人工审核**照常**；
   权威接口地址与参数在**管理员后台自定义**（对接哪些渠道后续再定）；当前先实现人工审核。

这两条把两个悬而未决的问题变成了硬约束：

- 住客侧的会话体系怎么建（ADR-018 §6 留的"是否复用 user_session"）；
- 实名的 `PENDING` 状态靠什么变成 `VERIFIED`（ADR-018 §6 留的"核验渠道"）。

## 2. 决策

### 2.1 三张会话表，物理分开

`user_session`（员工，存量）、`guest_session`（住客，V15 新增）、`platform_session`（平台，V15 新增）。

**为什么不共用一张表加 `surface` 列**：共用意味着每一条会话查询都必须记得带
`surface = ?`。漏一次，一个住客令牌就能在商家侧被认出来——而这正是"杜绝越权"
要防的事。这与 ADR-016 拒绝"tenant_id 可空"是同一个论证：**隔离要在结构上成立，
不能依赖每个查询都写对**。分表之后，认证代码查错表就是查不到，不存在"忘了带条件"。

代价是三份相似的表结构与三份相似的服务代码。这个代价是买隔离的钱，不是浪费。

### 2.2 令牌哈希域分离

三个平面的令牌入库哈希各不相同：

| 平面 | 派生方式 |
| --- | --- |
| 员工（存量，不迁移） | `SHA-256(token)` |
| 住客 | `SHA-256("guest-session:v1:" \|\| token)` |
| 平台 | `SHA-256("platform-session:v1:" \|\| token)` |

**为什么值得多套一层前缀**：没有前缀时，同一个令牌串在三张表里的哈希完全相同。
此时只要有人写出"先查 A 表、查不到兜底查 B 表"这种看着挺健壮的代码，
一个平面的令牌就会被另一个平面认出来。加了域前缀，这类兜底查询**不可能命中**——
即使有人写了，也只是查不到而已。

员工平面保持无前缀是为了**不迁移存量会话**（改派生方式会踢掉所有在线员工）。

派生实现只有一处（`SessionTokens.hashInDomain`），各平面通过自己的
`GuestSessionTokens` / `PlatformSessionTokens` 声明域常量。直接在别处写 `SHA-256`
属于绕过本决策。

### 2.3 三条安全链，按路径前缀划分

`SecurityConfig` 拆成三条 `SecurityFilterChain`：

| 链 | 路径 | 认的令牌 |
| --- | --- | --- |
| guestChain (Order 1) | `/api/v1/guest/**` | 只认 `guest_session` |
| platformChain (Order 2) | `/api/v1/platform/**` | 只认 `platform_session` |
| apiChain (Order 3) | 其余 | 只认 `user_session` |

**为什么不用一条链判断"令牌属于哪个平面"**：单链方案下认证过滤器必须依次尝试
三张表，任何一次"顺手兜底"就是一条跨平面通路。分链之后，跨平面访问的失败形态
是稳定的 401，不依赖任何 `if`。

配套两条纪律：

- **住客与平台过滤器绝不绑定 `TenantContextHolder`**。一旦绑定，任何按"当前租户"
  取数的代码都会把住客/平台调用当成某个租户的调用方。
- 三个平面的**主体类型互不实现**：`PmsPrincipal`（带 tenantId/hotelIds/permissions）、
  `GuestPrincipal`（无任何租户字段）、`PlatformPrincipal`（动作码集合）。类型不同，
  写错就是编译不过。

### 2.4 平台动作独立于租户权限字典

平台权限是**动作码直授**（`platform_user_action`），字典在 `platform_action` 表，
与租户的 `permission` 表完全分开。理由：两套授权模型不同（租户是"资源:动作"带门店范围，
平台是"平面动作"无数据范围），混在一张表里迟早有人给平台账号授一个租户权限点。

本轮不引入平台角色层：平台账号数量是个位数到十几，多一层分组只增加配错机会；
审计要的是"谁在何时做了什么动作"，直授反而更直接。账号数量增长后再引入角色分组，
届时 `platform_user_action` 的语义不变（仍是最终生效的动作集合）。

本轮 4 个动作：`guest.verification.read` / `guest.verification.review` /
`guest.channel.read` / `guest.channel.write`。**刻意不含**"跨租户查看租户业务数据"——
平台不跨租户（DEC-02）。

### 2.5 实名决定走唯一入口

人工审核与（将来的）权威渠道都调 `GuestVerificationDecisionService.decide()`，
区别只在 `source`（`MANUAL` / `AUTHORITY:<channelCode>`）。状态机、并发控制、留痕
只有一份实现。

**本服务的构造器里没有渠道相关依赖——这是"权威接口熔断时人工审核照常"的实现保证。**
不是靠一个 if 判断跳过渠道，而是人工路径结构上没有读渠道的能力。想让熔断影响
人工审核，得先改构造器——那是一次会被 code review 看见的改动。

其它的关键设计（已在实现中体现）：

- **审核者从会话取**，不从请求体取——留痕的价值全在"这条是谁做的"；
- **决定必填理由**（库层 CHECK 兜底）——没有理由的"通过"事后无法复核；
- **并发防线在 SQL**：`WHERE status = 'PENDING'`，第二个审核员得到 409 而不是
  静默覆盖；
- **驳回不写 `verified_at`**——那一列的语义是"何时验证通过"，写上会把驳回的
  也算进"已实名"统计；
- **留痕自带掩码快照**——档案被重新提交覆盖后，"当时审的是哪一份"仍可追溯。

### 2.6 核验渠道是配置载体，不是实现

`guest_verification_channel` 表存渠道配置（code / kind / endpoint / credentialRef /
timeout / priority）与熔断状态（circuit_state / consecutive_failures / opened_until）。

- 本轮**没有任何 AUTHORITY 实现**。配置填好了也只是存着；接口返回体带
  `implementationAvailable` 标记，人工渠道恒为 true、权威渠道按已注册实现判断。
  让配置界面照实说"配了但没接通"，比让人在真实住客进来时才发现全部卡在人工队列强。
- **凭据只存引用**（credentialRef 指向密钥管理），配置表会被导出、会进工单，
  密钥进了这张表就等于进了所有备份。
- **人工渠道不允许停用**（服务层拒绝）：它是权威接口熔断时唯一的兜底，
  停掉它等于在权威接口抖动的那一刻让所有新住客注册卡死。
- 熔断**自动恢复**：`openedUntil` 到点后由下一次调用转 HALF_OPEN 试探；
  另有**手动复位**（必须给原因，原因写进 lastFailureReason 留档）——
  配置填错导致的失败会让状态来回跳，从状态本身看不清"到底修没修好"。

### 2.7 平台账号也有强制首改

种子创建的平台账号 `must_change_password = true`，在改掉初始口令之前，平台平面里
除改密/登出/`me` 外全部 403（`PASSWORD_CHANGE_REQUIRED`）。改密后撤销**其它**
全部会话（保留发起者）——平台动作影响面是全局的，口令刚被改掉最合理的解释就是
"原口令可能已泄露"。

### 2.8 审核为什么必须是平台身份

实名数据在住客平面，不属于任何租户。让酒店前台能读客人身份证是最典型的内部数据
滥用；"某家店审自己的客人"还会带来竞争性滥用。平台侧集中审核 + 留痕，才有可追责
的对象。这不违反"平台不跨租户"：它不涉及任何租户的业务数据。

### 2.9 住客登录方式：用户名密码先行，其余走控制台开关（2026-11-01 追加）

需求方追加两条：住客登录**再加一个"用户名"方式**，先支持基础的用户名+密码；
手机号、邮箱等登录项**在管理员控制台去设置**。

**密码是凭证的属性，不是账户的属性。** 用户名+密码是一对，存放在
`guest_credential`（`provider=USERNAME, subject=用户名, secret_hash=BCrypt`），
与"换手机号不影响实名结论"是同一条分界。其它 provider 的 `secret_hash` 必须为空
（库层 CHECK）：第三方凭据在外面（OAuth token），库里有 secret 会让人误以为我们在存它。

**用户名注册即视为归属已验证**（`verified_at = now`）："知道密码"本身就是归属证明，
与员工账号首次开通同一逻辑；其余方式仍需外部验证（`requiresOwnershipProof()`）。
用户名规范化为小写——`Admin` 与 `admin` 必须是同一个账号。

**可用性 = 实现状态（代码）∧ 策略开关（`guest_login_policy` 表）**。这条双条件
是本节最重要的决策：

| 场景 | 代码 | 开关 | 对外 |
| --- | --- | --- | --- |
| USERNAME | 已实现 | 开 | 可用 |
| USERNAME 被暂时关停 | 已实现 | 关 | 未开放（403） |
| PHONE 提前配好等上线 | 未实现 | 开 | **仍未开放** |
| PHONE（默认） | 未实现 | 关 | 未开放 |

收益：**"接通新通道"永远是一次代码发布，"暂时关停"永远是控制台一个开关**，
两者不会混。未实现的方式允许打开开关（运维"提前配好等上线"是正常节奏），
界面按 `implemented=false` 如实标注"配了但没接通"——与 §2.6 的
`implementationAvailable` 同一套诚实原则。

登录失败**统一为"用户名或密码不正确"**：用户名不存在、密码错、账户已关闭三个分支
对攻击者的价值不同（是否存在这个用户名），统一后登录接口不构成账号枚举器。
方式未开放（403）与凭据无效（401）刻意分开：前者描述**方式**、不涉及账号，可以明说。

"登录方式未开放"用 403 与"凭据无效"（401）分开：前者说的是**方式**、不涉及账号，
可以给明确文案让用户换方式；后者必须统一话术。混成一个响应要么泄露开关状态，
要么让被关方式的使用者反复试密码。

**登录方式清单是匿名接口**（`/guest/auth/methods`）：登录页在登录前就要读它来渲染按钮。

### 2.10 归属挑战的发送通道：SPI + 路由，EMAIL 先行（R-20261101-33 建立，R-20261102-01 接通）

绑定 PHONE/EMAIL 的归属证明是**挑战-响应**：向目标发 6 位验证码，提交正确的码才允许绑定。
码的存储与校验（哈希落库、5 次尝试上限、10 分钟过期、一次性消费）与通道无关，
所以通道做成 SPI（`OwnershipChallengeSender`），接通新方式不改机制。

**方式 → 实现的分发由路由器集中完成**（`ChallengeSenderRouter`）：按
`supports(provider)` 与 `@Order`（真实通道 0 优先、dev 信箱 100 兕底）选第一个
支持该方式的实现；**没有任何实现支持时抛 503**（`ChallengeDeliveryUnavailableException`），
绝不静默跳过——静默成功等于声称"验证码已发出"，用户收不到码会反复重试直到挑战过期。
曾经存在的 `NoopOwnershipChallengeSender` 占位已删除：路由器对空列表的处理
就是同一语义，且保证集中在一处而不是散在实现里。

**EMAIL 用 SMTP 接通**（`MailOwnershipChallengeSender`，默认关闭，`mail.enabled` 显式开）：

- 不启用 `spring.mail.*` 自动配置——host/port/from 属于"归属验证"这一个用途，
  不是全局邮件能力；将来别的功能要发信应另立通道，不共用发件人声誉。
- 发送失败包装为 503（与"未接通"同一处置），绝不裸抛 `MailException` 变 500；
  验证码不进日志、不进异常 message（那是给排障者看的）。
- 本地/CI/预发的收信端是 compose 里的 **MailPit**（SMTP 宿主 55025、Web UI 8025），
  与 PostgreSQL、RabbitMQ 同一份编排；预发/生产改指真实内网中继即可，代码零改动。
- `mail.enabled` 与 `dev-mailbox` 可同时开：EMAIL 走真实 SMTP、PHONE 落信箱——
  真实通道优先的路由顺序保证这个组合不互相遮蔽。

**PHONE（短信）继续等待服务商签约**：企业资质与账号是外部授权（与 S5-01 渠道授权
同性质），本地伪造不出有意义的"真实验证"。接通时只需新增一个
`supports("PHONE")` 的实现，机制与路由零改动。

**验证码登录是消费侧，不在本节**：本轮接通的是"绑定"的投递能力；
用 EMAIL+验证码**登录**需要新的登录入口（发起挑战 → 确认 → 发会话），
是独立的后续工作，`isImplemented()` 在那之前仍只标 USERNAME。

## 3. 被否决的替代方案

- **一张会话表 + surface 列**：隔离依赖每个查询写对条件。否决，理由见 §2.1。
- **复用 `app_user`（tenant_id 放宽为可空）承载平台账号**：会让所有租户查询出现
  可空分支，且伪造"平台租户"会让租户列表多出假数据。否决。
- **确定性加密兼做实名判重**：ADR-018 已否决（泄露相等性、密钥泄漏即全量失效）。
- **人工审核路径里读渠道状态**（"跳过熔断的渠道"）：看似更灵活，实则把两条通道
  耦合在了一起——渠道表出问题（误清空、误配置）会连带人工审核不可用。否决，
  改为结构隔离（§2.5）。
- **发送器继续用"唯一实现"注入（`ObjectProvider#getIfAvailable`）**：EMAIL 接通后
  同一进程必然出现"真实通道 + dev 信箱"两个实现，多候选直接抛
  `NoUniqueBeanDefinitionException`。否决，改为 §2.10 的路由器集中分发。
- **把验证码放进挑战响应体**：挑战响应发给的是"发起绑定的人"，而归属验证要
  确认的是"目标邮箱/手机号的主人"——放进响应等于允许任何登录用户绑定任何
  目标（账户接管只需一个会话）。否决，见 `DevChallengeMailbox` 的注释。

## 4. 后果

**正面**：

- 三平面的令牌在库层不可互换，"杜绝越权"有了结构保证而非约定；
- 人工审核闭环可用且留痕完整，不依赖任何外部服务可用性；
- 权威渠道的接入只是"新增一个 source + 一个实现类"，状态机与留痕零改动。

**负面 / 代价**：

- 三份相似的会话代码。接受：这是买隔离的钱；
- 本轮没有住客登录 HTTP 接口（验证码/OAuth 未接），会话机制只能经测试验证；
- 平台端没有前端工程，审核操作暂只能走 API（`frontend/platform-ops/` 待初始化）。
