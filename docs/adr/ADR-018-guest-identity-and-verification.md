# ADR-018：住客身份、实名与主 ID

> 日期：2026-11-01（AEST）；任务：S4-01 前置。
>
> 状态：**已定案并落地模型**（登录接口与会话留下轮，见 §6）。
>
> 关联：[ADR-017 多端与身份平面](./ADR-017-multi-surface-and-identity-planes.md)、
> [ADR-016 认证与租户隔离](./ADR-016-authn-authz-tenant-isolation.md)、
> [DEC-10](../requirements/decision-register.md)（已定案）、[DEC-12](../requirements/decision-register.md)（个人数据保留）、
> [DEC-17](../requirements/decision-register.md)（企业对公账户，另议）。

## 1. 背景

需求方给定住客侧的身份口径：

1. 登录方式：**手机号、邮箱**，以及第三方——**微信、QQ、国家统一身份认证、Apple** 等；
2. **不论用哪种方式注册进入，首先要实名认证**；
3. 实名凭据是**身份证号，必须加密存储**；
4. 需要一个**主身份 id**；有账户后可以再**绑定**其他第三方登录源；
5. 企业对公账户（差旅、单位替员工订房、单位统一身份/域账户登录）另提，见 DEC-17。

要回答的是五个具体问题：主 id 是什么、一人多登录方式怎么归并、身份证号加密后怎么保证不重复、
强制实名怎么执行、住客表与租户表什么关系。

## 2. 决策

### 2.1 三层结构：账户 / 凭证 / 实名档案

```
guest_account          主身份（UUID，无 tenant_id）
├── guest_credential   (provider, subject) → account_id    一人多份
└── guest_id_verification  身份证号密文 + HMAC 索引          一人一份
```

**为什么凭证与实名必须分开**：

- 换手机号不该影响实名结论——实名验的是**人**，不是号码；
- 绑微信不该再验一次身份证——否则每加一个登录方式就多一次核验成本与失败点；
- 实名档案是"一个人一份"，凭证是"一个人多份"，放在一张表里必然出现"同一人两条实名记录"。

### 2.2 主 ID

- `guest_account.id`：**服务端生成的 UUID**，客户端**永不感知**。
  对外定位一律用不可猜测的引用，绝不用身份证号或手机号当标识（与 ADR-017 §2.6 同一条原则）。
- 主 id **永不变**：订单、发票、审计、对公账单都指向它。手机号换绑、身份证换证都不影响。
- 一个自然人原则上一份账户。重复注册的合并流程尚未定（§6），因此本轮**不实现自动合并**。

### 2.3 凭证（provider + subject）

| provider | subject 规范化 | 说明 |
| --- | --- | --- |
| `PHONE` | E.164（`+86...`） | 主登录方式之一 |
| `EMAIL` | 全小写 | 主登录方式之一 |
| `WECHAT` | **unionid 优先**，无则 openid | 同主体下多个小程序/公众号的 openid 不同，unionid 才稳定 |
| `QQ` | 开放平台 openid | — |
| `CNID_SSO` | 对方返回的稳定 sub | 国家统一身份认证 |
| `APPLE` | `sub` | Apple 的邮箱可能是中继地址，不能拿邮箱当标识 |
| `CORP_SSO` | 对手方 `sub` + 企业标识 | **预留**，等 DEC-17 |

- 唯一约束 `(provider, subject)` 建在库层：同一凭证**只能**指向一个账户。
- 绑定必须证明"你确实是这个凭证的主人"：手机/邮箱走验证码，第三方走 OAuth 回调。
  **本轮只落模型，验证码与 OAuth 在登录轮实现**——没有验证的绑定等于允许抢占别人的手机号。

### 2.4 身份证号：加密 + HMAC 双列（核心设计）

需求有两面：**不能明文存**，同时**同一身份证不能绑两个账户**。单靠一种手段做不到，所以用两列：

| 目的 | 手段 |
| --- | --- |
| 机密性 | **AES-256-GCM**，密文格式 `v1 ‖ nonce(12) ‖ ciphertext ‖ tag(16)`，Base64 后存 `text` |
| 查重 / 唯一性 | 另存 **HMAC-SHA256(规范化后的号码)** 十六进制，建**唯一索引** |
| 人工核验 | 默认只返回**掩码**（前 6 位 + 后 4 位）；全量明文只在受审计的取证流程里解密 |

**为什么不用确定性加密兼做查重**：确定性加密让同一明文得到同一密文，看着正好能查重，
但它把"两条记录是否同一个人"泄露给任何能读表的人，而且密钥一旦泄漏，**所有历史记录同时失效**
（无法只换新数据）。HMAC 索引同样泄露相等性，但它是单向的，且可以用**独立密钥**轮换。

**为什么不直接用哈希**：身份证号的空间很小（18 位，且含地区码与校验位结构），
暴力枚举完全可行——纯哈希等于明文。必须带密钥（HMAC）。

**密钥管理**：

- `pms.guest.pii-key`（AES-256，Base64）与 `pms.guest.pii-hmac-key`（**独立**密钥）；
- 从环境变量或密钥管理服务注入，**不进代码库、不进迁移脚本、不进示例配置**；
- **启动即校验**：缺密钥直接启动失败。绝不允"没配就跑起来、悄悄存明文"这种降级；
- 两个密钥分开的理由：索引密钥泄漏只影响"能否查重"，不会让密文可解。

### 2.5 强制实名

状态机：`UNVERIFIED → PENDING → VERIFIED / REJECTED`

- 注册成功即为 `UNVERIFIED`；提交实名资料 → `PENDING`；核验通过 → `VERIFIED`；
- **未 `VERIFIED` 只允许**：提交/查看自己的实名状态、登出、注销账号；
  其它一律拒绝（服务端拦截器，与 `PasswordChangeRequiredInterceptor` 同一手法，不做前端跳转）；
- 需求方原话是"首先就要实名认证"，所以**实名是使用前置条件，不是加分项**。

**本轮的边界要说清**：核验渠道（是否对接权威实名核验接口）尚未定案，
所以本轮只做到"采集 + 加密存储 + 状态机"，状态停在 `PENDING`。
**不伪造 `VERIFIED`**——那是把"采集了"说成"验过了"。

### 2.6 住客表不带 `tenant_id`：第一张例外表

现有所有业务表都带 `tenant_id`，`IdentityMapper` 甚至刻意"不存在不带 tenantId 的查询方法"。
住客表必须例外：住客不属于任何租户。

一个例外会削弱一条已经建立的规则，所以必须配三条约束：

1. **跨平面只许单向引用**：租户业务表**可以**引用 `guest_account.id`
   （订单属于某租户，由某个住客下单）；住客表**不得**引用任何租户业务表。
   理由是攻击面方向：住客侧是面向公网、最可能被打穿的一侧，
   一旦它能顺着外键读到租户数据，整条隔离线就绕过去了。
2. **不参与租户范围**：住客表不进租户导出、不进按租户的备份恢复演练清单，
   数据主体与保留策略不同（DEC-12）。
3. **命名与结构上标出来**：包名 `guest`、表名前缀 `guest_`、mapper 注释写明"本表无 tenant_id，
   不可用于租户业务"。

### 2.7 本轮不做

| 项 | 原因 |
| --- | --- |
| 住客登录接口与会话 | GUEST 令牌是否复用 `user_session` 需要单独决定：复用会让员工会话与住客会话共用撤销逻辑，不复用则要第二套会话表。**下一轮专项** |
| 验证码 / OAuth 回调 | 属登录轮 |
| 实名外部核验 | 渠道未定（§6） |
| 企业对公账户与统一身份 | DEC-17，需先定"企业≠租户" |
| 账号注销 | 与 DEC-12 数据保留联动 |

## 3. 被拒的备选

| 备选 | 为什么不做 |
| --- | --- |
| 用手机号作主 id | 换号即换人；且手机号是 PII，当外键会让它扩散到所有关联表 |
| 用身份证号作主 id | 同上，而且无法注销/换证 |
| 把住客凭证并进员工表 `app_user` | 见 ADR-017 §2.1：外部消费者与内部员工共用一套权限体系，一次配错就是越权 |
| 身份证号明文 + 权限控制 | 备份、慢查询日志、DBA、导出都能看到；一次拖库等于全量泄露 |
| 只加密不建 HMAC 索引 | 无法判重，同一人可注册多个账户绕过风控与实名限制 |
| 确定性加密兼做查重 | 泄露相等性；密钥泄漏即全量失效（见 §2.4） |
| 实名做成"可跳过、后续补" | 需求方明确"首先就要实名"；可跳过等于没有 |

## 4. 后果

- 新增 3 张表，其中 `guest_account` 是全库**第一张没有 `tenant_id` 的业务表**；
- 新增两个**必须配置**的密钥，缺了服务起不来——这是有意为之；
- 客服核验身份证只能看掩码，要看全量得走受审计的解密流程（成本换来的是"拖库不等于泄露"）；
- 住客侧的代码与租户侧在包结构上分开（`guest` 包），避免混写。

## 5. 回退路径

若后续要求"住客可自助修改身份证号"，当前"一份档案一个版本"的模型需要加版本表。
改动局限在 `guest_id_verification`，主 id 与凭证绑定不受影响。
