# ADR-016：认证、授权与租户隔离方式

> 日期：2026-10-30（AEST）；任务：S1-03。
>
> 状态：**已选定并落地**（实现 + 集成测试 + 运行态冒烟已通过）。
>
> 关联：[开发规划 §4.3 S1-03](../企业级酒店%20PMS%20开发任务规划.md)、[需求范围 §4.1](../requirements/scope.md)、[功能清单 A/B 域](../development/feature-catalog.md)、[进度台账 R-20261030-04](../development/progress.md)、[ADR-001 库存权威](./ADR-001-inventory-authority.md)、[S1-03 验证记录](../verification/S1-03/2026-10-30-authn-authz.md)。

## 1. 背景

S1-02 已落地组织基线（租户 / 集团 / 门店），但系统当时**没有任何可用的登录方式**：安全链默认拒绝一切业务请求（S1-01）。

S1-03 需要回答四个问题，且必须与既有铁律兼容（PostgreSQL 是事实源、租户来自可信身份而非请求体、外部 HTTP 不进步骤事务）：

1. 凭据形态：自包含 JWT，还是服务端会话？
2. 撤权语义：B-04 要求「撤权后旧会话按约定失效」，允许多长延迟？
3. 隔离实现：靠应用层 `WHERE tenant_id = ?`，还是启用 PostgreSQL 行级安全（RLS）？
4. CSRF：无状态 JSON API 是否还需要令牌？

## 2. 决策

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 凭据形态 | **不透明随机会话令牌**（32 字节，Base64URL，43 字符），`Authorization: Bearer <token>` | 自包含 JWT 的最大问题是无法即时撤销：要么短过期 + 刷新令牌（复杂度不减），要么维护黑名单（等于还是要查库）。既然撤权必须即时，直接查库更简单 |
| 令牌存储 | 库内只存 SHA-256 十六进制（64 字符），明文只在登录响应出现一次 | 库被读取时不等于会话被接管；令牌高熵，不需要 BCrypt 这类慢哈希（每请求一次 BCrypt 会拖垮整个 API） |
| 会话表 | `user_session`：`issued_at` / `expires_at` / `revoked_at` / `revoke_reason` | 撤销是数据变更而不是内存状态，重启不丢；`revoke_reason` 区分 LOGOUT / PASSWORD_CHANGED / ADMIN_REVOKED，审计可查 |
| 会话有效期 | 默认 8 小时（`pms.security.session-ttl`，ISO-8601），**不做滑动续期** | 续期语义（多长、按什么事件续）属于产品规则，等 S3-01 前端接入时定；先给固定窗口比"先这样滑着"更容易改 |
| 撤权延迟 | **下一个请求即生效**（会话校验每次现读账号、租户、角色状态） | 权限点与门店范围不写进令牌、不做请求级缓存，因此调岗、停角色、停门店、停账号、停租户都立即生效，无需失效广播 |
| 口令派生 | BCrypt（强度 10） | Spring Security 内置、成本可调；口令策略下限 12 位（NIST SP 800-63B） |
| 隔离实现 | **不启用 RLS**。所有查询强制带 `tenant_id`；跨表一致性用 `(id, tenant_id)` 复合唯一 + 复合外键 | 见 §3。RLS 需要每连接设置 `app.tenant_id` 并保证归还连接池前清理，这一层清理本身要独立测试；当前用"编译期就没有不带租户的查询方法"更划算 |
| 权限模型 | 全局权限点字典 `资源:动作`（`permission`）+ 租户内角色（`role`）+ `role_permission` / `user_role` | 权限名是代码常量，租户差异体现在"哪个角色拿到哪些权限点"；否则每个租户自定义权限名会让代码分支爆炸 |
| 门店数据范围 | `user_hotel_scope`，**空集合表示无任何门店权限**，不是全部 | 空集=全集是最常见的提权漏洞；`Authz.requireHotel` / `requireAllHotels` 对空与越界一视同仁地拒绝 |
| 批量语义 | 全有或全无 | 部分执行会让调用方从结果反推越界对象存在性 |
| 404 vs 403 | 不属于当前租户的对象一律 404 | 403 等于确认"该 id 存在"，属于对象存在性泄露（BL-07） |
| CSRF | 保持关闭 | 凭据在 `Authorization` 头里，浏览器不会自动携带；没有 Cookie 就没有跨站自动凭证面。**一旦改回 Cookie 会话，必须先开 CSRF** |
| 认证入口 | 仅 `POST /api/v1/auth/login` 匿名，登录体里接受 `tenantCode` | 登录前没有身份，只能用租户编码定位账号；这是唯一允许从请求体读取租户归属的地方 |

## 3. 被拒的备选

| 备选 | 拒绝理由 |
| --- | --- |
| JWT（HS256/RS256），撤权靠短过期 | 与 B-04「撤权后旧会话立即失效」直接冲突；补黑名单等于又回库查一次，还多一套密钥轮换与时钟同步问题 |
| JWT + 令牌版本号（每次请求比对版本） | 每请求仍要读一次版本号，成本与查会话行相同，却额外承担签名验证、`alg` 混淆、密钥轮换的实现风险 |
| Cookie 会话（`HttpOnly` + `SameSite`） | 管理端是独立 SPA，跨域 Cookie 需要 CORS + `SameSite=None` + CSRF 令牌三件套；Bearer 头在跨域下更简单，且不引入自动凭证面 |
| 现在就上 RLS | 需要：①每连接设置会话变量 ②连接池归还前清理 ③迁移账号与运行账号分别授权 ④所有 `SET LOCAL` 在事务内的正确位置。当前没有并发与连接复用压测（S1-13），先上 RLS 会得到"看起来更安全但没有证据"的结果 |
| 把权限点缓存进令牌或进程内 Map | 撤权延迟从"下一个请求"退化到"缓存过期"，与 B-04 冲突 |

### 3.1 RLS 的启用条件（不是"永不做"）

满足以下全部条件后重新评估，届时新开 ADR 取代本条：

1. S1-13 已有并发与连接复用测试，能验证"归还连接池后不残留租户变量"；
2. 存在跨租户读取路径（如总部跨主体报表，DEC-01/DEC-02 定案后的 A-05），应用层条件难以穷举；
3. 应用账号与迁移账号分权已稳定（S1-02 已具备），可以给 RLS 策略单独授权。

## 4. 后果

**正面**

- 撤权、停账号、停租户、停角色、调整门店范围**立即生效**，不需要任何失效广播或缓存清理。
- 会话是数据：可以按用户、按时间、按原因审计与回收，这是后续「强制下线」「运维排查」的基础。
- 编译期约束：`IdentityMapper` 不存在不带 `tenantId` 的查询方法，"先按 id 查到再判断归属"的写法在代码层面不成立。

**代价**

- 每个已认证请求多 3 次查询（会话联表、权限点、门店范围）。当前可接受；S2-06 接入监控后按 P95 决定是否加**进程内**短缓存（上限 5 秒，且必须在撤权路径显式失效）。
- 会话表需要清理策略（过期行归档），留给 S6-03（备份归档与 PITR）。
- `last_seen_at` 当前只在登录与改密时写入，不逐请求更新，因此无法据此做"闲置超时"。闲置超时属于产品规则，等定案。

## 5. 回退路径

- 若改为 Cookie 会话：保留 `user_session` 表与全部服务方法，只换传输方式；**必须同时打开 CSRF 并补同步令牌**，并增加 `SameSite` / `Secure` 配置与跨域 CORS 白名单。
- 若改为 JWT：`user_session` 降级为"撤销列表"，`revoke_reason` 语义不变；`authenticate` 改为"验签 + 查撤销表"。
