## 1. 背景

需求方提出 SaaS 平台需要 6 个端：

| # | 端 | 使用者 |
| --- | --- | --- |
| 1 | H5 客户端 | 住客（手机浏览器 / 微信内） |
| 2 | Web 客户端 | 住客（桌面浏览器） |
| 3 | Web 商家端 | 酒店员工：前台、客房、店长、财务 |
| 4 | H5 商家端 | 酒店员工（移动：查房态、办入住、接通知） |
| 5 | 平台业务管理端 | 平台业务人员：客服、售后、运营 |
| 6 | 平台管理员端 | 平台系统人员：技术、数据库、组织架构、存储 |

当前只有第 3 个（`frontend-admin-pro/`），其余 5 个都不存在。

**如果按字面直接铺 5 个新前端工程，最贵的错误会被固化**：把平台端的"跨租户"能力塞进租户内的权限体系。
所以本 ADR 先回答"这些端的用户属于哪条身份平面"，再谈工程数量。

## 2. 决策

### 2.1 核心：三条身份平面，而不是六个端

6 个端收敛为 **3 条身份平面**。平面决定"身份从哪来、能看多少数据"，端只决定"用什么界面"。

| 平面 | 身份来源 | 数据范围 | 会话 | 现状 |
| --- | --- | --- | --- | --- |
| **TENANT**（商家） | `app_user`（带 `tenant_id`）+ 服务端会话 | 严格限定在本租户 + `user_hotel_scope` 门店范围 | `user_session`，不透明 Bearer | **已落地**（ADR-016） |
| **GUEST**（住客） | 待定（手机号/微信，DEC-10） | **一个租户都不属于**；只能看公开目录 + 自己的订单 | 独立会话，与员工会话不通用 | **未开始**，J-01 卡 DEC-10 |
| **PLATFORM**（平台） | 独立身份表（不能复用 `app_user`） | **不跨租户**。只有两类权限：①**系统资源**——日志清理/审计/溯源取证、新增业务数据库、多个对象存储配置；②**限时支持会话**——经批准后进入**单个**租户，到期自动失效 | 独立会话 + 强制审计 | **未开始**；DEC-02 已部分定案（不跨租户），支持会话细则待定 |

**"不跨租户"的准确含义**（需求方 2026-11-01 明确）：平台**不存在**任何
"一次看到所有租户业务数据"的权限或接口——没有全平台的订单查询、没有跨租户报表。
但平台业务人员（客服/售后/运营）确实要处理某家商家的问题，做法是**限时支持会话**：
经批准进入**某一个**租户，在租户内按最小权限操作，全程留痕，到期自动失效。
这不是"跨租户视图"，而是"一次只在一个租户里，且必须有人批准"。

这条区分很实用：它把最容易做歪的一类权限（"平台超管"）换成了一次可审计的、有始有终的动作。

**为什么不能把三条平面塞进一个 `app_user`：**

- `app_user` 带 `tenant_id`，且 ADR-016 的隔离前提是"编译期就不存在不带租户的查询方法"。
- 平台运维要跨租户 → 只能给 `tenant_id` 加可空列，或伪造一个"平台租户"。
  前者让所有租户过滤出现一个可空分支（隔离靠"每个查询都记得写 `IS NULL` 分支"，这正是最容易漏的地方）；
  后者让跨租户能力被租户边界挡住，实际做不了事。
- 住客根本不该出现在员工身份表里：一套权限体系同时服务"内部员工"和"外部消费者"，
  任何一次角色配置失误都会让外部人拿到内部能力。

**结论**：三条平面各自独立的身份表与会话表，**不共享授权模型**。
平台端不复用 `role`/`permission`（那是租户内的业务权限），平台权限是另一套"平台动作"清单。

### 2.2 六个端的归位

| 端 | 平面 | 承载功能域 | 状态 | 依赖 |
| --- | --- | --- | --- | --- |
| Web 商家端 | TENANT | O 域（现 `frontend-admin-pro/`） | 主体已交付 | — |
| H5 商家端 | TENANT | O-12（新增） | TODO | 无阻塞；需先定"移动端承载哪些动作" |
| H5 客户端 | GUEST | J-06 | TODO | J-02（本轮已开工）、J-05 限流、J-01 卡 DEC-10 |
| Web 客户端 | GUEST | J-10（新增） | TODO | 同 H5 客户端，共用同一代码库 |
| 平台业务管理端 | PLATFORM（支持会话） | A-07（新增）+ A-05 | 待定：支持会话细则 | DEC-02 已定"不跨租户"；待定支持会话的审批/时限 |
| 平台管理员端 | PLATFORM（系统资源） | A-08（新增） | 待定：范围已确认，见 §2.4 | 不含租户业务数据；实现排在日志/存储/数据库配置之后 |

**客户端的正确开工顺序**：`J-02 公开目录（可售查询）` → `J-05 限流与防刷` → `J-06/J-10 界面` → `J-01 住客身份（DEC-10）` → `J-03/J-04 我的订单与取消`。
理由：前两步不需要任何未决项；第三步之后的"我的订单"必须绑定住客身份，硬跳到那里只能做一个假登录。

### 2.3 技术选型

| 端 | 选型 | 理由 |
| --- | --- | --- |
| Web 商家端 | Ant Design Pro 6（**已定**，ADR-015） | 复杂后台 + ProTable/ProForm 的密度优势 |
| H5 商家端 | Vite + React + antd-mobile | 移动端表单与列表与 Pro 组件范式不同，硬做响应式会把桌面版拖成一坨 |
| H5 客户端 / Web 客户端 | **同一个代码库**，两套断点；Vite + React | 客户端是"看房型→下单→查订单"，桌面与移动只有版式差异，拆两个工程等于双份维护 |
| 平台业务管理端 | Ant Design Pro（另一份工程） | 与商家端同范式，但**独立部署、独立域名**：客服能看到跨租户工单，不能和商家端共用产物 |
| 平台管理员端 | **见 §2.4**，倾向"运维控制台"而非"能改数据库的网页" | — |

**各端共享什么**：`docs/api/openapi-v1.json` 契约 + `scripts/gen-pms-types.mjs` 生成的前端类型 + 错误三分类约定（`errors.ts` 的心智模型）。
**不共享**：不建 npm workspace。首期各端独立 `node_modules`，避免构建耦合把"改一个端要重装所有端"这种成本提前引进来。

**技术选型修订（需求方指示，2026-11-02）**：Web 端**统一 Ant Design Pro**——
C 端 Web 客户端从"Vite 两断点同库"改为独立的 AntD Pro 工程（`guest/`），
H5 与小程序**暂缓**（只建目录放 README，等后端面与产品节奏）；
企业商旅控制台（`corp-portal/`，DEC-17）也按 AntD Pro 立骨架。落地顺序按需求方给的
优先级：①platform-admin（R-20261102-02 已交付）→②platform-ops→③merchant-web 扩展→
④guest Web→⑤corp-portal。**初始化方式**：克隆 merchant-web（同一份 package-lock，
依赖版本严格一致）后按身份平面改造——多端同栈后这是成本最低且不漂移的做法。
骨架先行**不改变**各端的 DEC 约束（DEC-01/02 仍约束平台端细化功能，DEC-17 仍 OPEN）：
骨架页只含列定义与真实空态，不渲染假数据。

### 2.4 平台管理员端的范围（**已由需求方确认 2026-11-01**）

需求方给的范围是"只做 SaaS 系统的关键操作"。据此把本端切成**配置与运维**，不含租户业务数据：

| 可做 | 具体内容 |
| --- | --- |
| 日志 | **清理**（按保留策略）、**审计**（谁在什么时候做了什么）、**溯源取证**（按 requestId / 主体追一条链路） |
| 数据库管理 | **新增业务数据库**、查看连接与迁移状态；即"配置数据源"，不是"执行任意 SQL" |
| 存储管理 | **编辑/新增对象存储配置**（多个并存），承载酒店图片、视频等资源 |
| 组织 | 租户与门店的增改（属配置，不是改别人的业务数据） |

| 明确不做 | 原因 |
| --- | --- |
| 任意 SQL / DDL 执行界面 | 应用账号 `pms_app` 故意没有 DDL 权限，迁移走独立 `pms_migrator`（ADR-011/016）。一个能跑任意 SQL 的网页等于把这条边界拆掉，而它一旦被打穿，损失是**整库**而不是一家门店 |
| 查看/导出身份证号等实名信息 | 实名数据在住客平面（ADR-018），取证要走独立受审计流程，不放在配置台里 |
| 修改租户业务数据（订单、房价、库存） | 那是租户自己的事；平台要协助就走**限时支持会话**（§2.1） |

**"新增业务数据库"的实际含义**：支持按租户/按业务维度配置多个数据源，为将来的
「SaaS 配置库与业务数据库拆分」铺路。需求方已明确那是**后期迁移**，前期不做、不影响业务运行；
所以本轮只把它记在路线图上，不建多数据源路由。

**"多个对象存储"的实际含义**：存储配置是一张表（类型/端点/桶/凭据引用/用途），
可以有多个并存，酒店图片与视频按用途路由到不同存储。凭据只保存**引用**（指向密钥管理），
不在配置表里存明文密钥。

### 2.5 仓库组织：`frontend/` 下多工程并列

**需求方决定拆成多个独立工程**（"避免单一前端太重"）。本条为最终结论，取代本 ADR 早期版本的
"不搬家"判断——那个判断的出发点是"减少迁移风险"，但拆分的收益（发布节奏、攻击面、产物体积）
大于一次目录迁移的成本，且迁移只在开始阶段做一次。

```
frontend/
├── merchant-web/     Web 商家端     Ant Design Pro 6       已可运行（原 frontend-admin-pro/）
├── merchant-h5/      H5 商家端      Vite + React + antd-mobile   待初始化
├── guest/            客户端(H5+Web) Vite + React + antd-mobile   待初始化，后端面未就绪
├── platform-ops/     平台业务管理端  Ant Design Pro 6       阻塞（DEC-01/02）
└── platform-admin/   平台管理员端    Ant Design Pro 6       阻塞（DEC-01/02）
```

**5 个工程对应 6 个端**：H5 客户端与 Web 客户端共用 `guest/`。两者是同一套业务流程，
差别只在版式与输入方式；拆开会让下单流程维护两遍且必然漂移。若将来确需独立发布，
复制目录即可，合在一起不会让那天变难。

**各工程独立依赖、独立构建、独立发布**，不建 npm workspace：
workspace 会把构建耦合提前引进来（改一个端触发全量重装），
而当前是单人主导，耦合成本大于收益。共享的是**文件**而不是包：
契约 JSON、类型生成脚本、错误三分类约定。

**迁移已完成的部分**（R-20261101-29）：`frontend-admin-pro/` → `frontend/merchant-web/`，
CI（`frontend.yml` / `beta.yml` / `release.yml`）、生成脚本（`gen-pms-types.mjs`、
`sync-menu-locales.mjs`、`sync-login-locales.mjs`）同步更新；
两个词条脚本原本写死作者本机绝对路径，一并改成仓库相对路径。
`docs/verification/**` 下的历史记录保留原路径，那是当时的证据，不做追溯改写。

**未完成的**：其余四个工程只有范围说明（各自的 `README.md`），没有代码。原因有两条：
新增工程需安装依赖，而本机 Agent 沙箱无法完成 `npm ci`（见 `docs/verification/S3-01a`），
必须在宿主终端执行；`guest/` 还缺后端面（J-05 限流未做、J-01 卡 DEC-10）。

**端之间的接口关系**：商家端与 H5 商家端复用同一批 API（`/api/v1/hotels/{hotelId}/...`），
**不需要新后端接口**——H5 商家端缺的是"移动场景要哪些动作"的产品判断，不是技术。
客户端与平台端需要新后端面：`/api/v1/public/**`（本轮已实现最小切片）与 `/api/v1/platform/**`（等 DEC）。

### 2.6 匿名公开面单独立前缀

- `/api/v1/public/**` 是**唯一**的匿名命名空间。新增匿名接口只能落在这个前缀下，
  便于用一条规则做限流、WAF、监控与"是否对外"的开关。
- **不用内部 UUID 定位资源**：客户端用 `(tenantCode, hotelCode)`，因为门店编码只在租户内唯一
  （`uq_hotel_code UNIQUE (tenant_id, code)`），而 UUID 外泄等于把内部标识送出去。
- **只返回公开字段**：不含总房数、已售数、内部 id；可售只给 `bookable` 布尔值。
  "仅剩 N 间"这类饥饿营销文案属产品决策，不在后端默认暴露。
- **默认关闭**（`pms.public-api.enabled=false`）。没有限流（J-05）之前**不对外暴露**：
  一个可被无限刷的匿名查询接口就是一台免费的库存探测机。

## 3. 被拒的备选

| 备选 | 为什么不做 |
| --- | --- |
| 一个前端工程 + 按角色隐藏菜单，充当"六个端" | 客户端与平台端的攻击面、发布节奏、资源体积、可用性目标完全不同；一个产物同时服务内外部用户，任何一次构建事故都同时影响两端 |
| 给 `app_user` 加可空 `tenant_id`，让平台账号"没有租户" | 见 §2.1。隔离从"编译期保证"退化成"每个查询记得写空分支" |
| 平台端复用租户内 `role`/`permission` | 平台动作（停租户、导出全量）与业务动作（改房价）语义不同，混在一张权限字典里会让"给客服加个权限"变成一次越权风险 |
| 每个端一个后端服务（微服务化） | 与 ADR-011 的模块化单体冲突；当前是单人开发，服务拆分会把部署与联调成本翻倍 |
| 平台管理员端直连数据库（DBA 网页） | 见 §2.4 |
| 客户端的"我的订单"先按订单号直查（不做身份） | 订单号可枚举，等于任何人都能查别人的订单。J-03 明确要求"不能凭订单 ID 越权" |

## 4. 后果

**必须新增（按顺序）**

1. 公开目录接口 + 限流（J-02 / J-05）——本轮开工 J-02。
2. 住客身份表与会话（J-01）——**等 DEC-10**。
3. 平台身份表、平台动作清单、支持会话与审计（A-05 / A-07 / A-08）——**等 DEC-01 / DEC-02**。
4. 各端工程（H5 商家端可先于客户端，因为它不需要新后端面）。

**代价**

- 三套身份表意味着三套登录流程与三套会话校验；这是为了隔离付的成本，接受。
- 平台端"不能改库"会让运维觉得不方便；用"工单 + 审计"补，不用"网页 + 便利"换。

**收益**

- 客户端不可能靠一次角色配置失误拿到内部权限（压根不在同一张表）。
- 平台端的跨租户动作可以逐条审计，而不是混在"某租户管理员"名下。

## 5. 已生效的分支：平台不跨租户（2026-11-01 定案）

本 ADR 初稿把"平台是否跨租户"留作待定，并写了两条分支。需求方已选择**不跨租户**，
因此 §2.1 的 PLATFORM 平面按下面这条落地：

- **系统资源**：日志（清理/审计/溯源取证）、数据库配置（新增业务数据库）、对象存储配置（多个）；
- **支持会话**：进单个租户、限时、留痕、到期失效（A-05）；
- **不存在**：全平台订单查询、跨租户报表、"平台超管"这类角色。

代价是平台业务人员处理问题时多一步（先申请支持会话），收益是不存在一个能一次看光所有租户的账号。
这一条也把 A-07/A-08 从"平面是否存在"的阻塞里释放出来，剩下的只是支持会话细则。
