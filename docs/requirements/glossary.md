# PMS 业务术语表

> 版本：0.1；日期：2026-10-19；任务：S0-01。
>
> 来源：[技术架构](../enterprise_hotel_pms_architecture.md) §3—§8；配套：[范围](./scope.md)、[业务决策](./decision-register.md)。英文名是沟通约定，不构成最终表名、API 字段或状态枚举的批准。

## 1. 组织与身份

| 编号 | 中文 / 英文 | 本项目含义 | 必须区分 |
| --- | --- | --- | --- |
| TERM-01 | 租户 / Tenant | 签约经营主体与业务数据隔离边界 | 不直接等同品牌、一个账号或一家门店；加盟归属见 DEC-01 |
| TERM-02 | 酒店集团 / Hotel Group | 租户内可选的组织管理层级 | 集团名称相同不能推导跨租户访问权 |
| TERM-03 | 门店 / Hotel | 实体房间、运营配置和酒店时区的归属单位 | 门店权限与功能权限分别管理 |
| TERM-04 | 员工账号 / Staff Identity | 进行后台业务操作的身份 | 账号身份不等于角色或门店数据范围 |
| TERM-05 | 角色 / Role | 一组功能权限的模板 | 有退款功能权限不等于可退任意门店订单 |
| TERM-06 | 数据范围 / Data Scope | 身份可以访问的租户、门店和对象集合 | 必须由服务端验证，不能信任客户端传值 |
| TERM-07 | 住客 / Customer or Guest | 自有预订入口的用户或实际入住人，语境中需明确 | 下单人、入住人、联系人和付款人可能不同 |
| TERM-08 | 渠道账号 / Channel Account | OTA 对接中实际获得授权的外部账户 | channel_id 是否已包含账户作用域需按真实协议决定 |

## 2. 客房、日期与预订

| 编号 | 中文 / 英文 | 本项目含义 | 必须区分 |
| --- | --- | --- | --- |
| TERM-09 | 房型 / Room Type | 具备共同销售属性的一类客房 | 房型可售数量不是某间实体房的占用事实 |
| TERM-10 | 实体客房 / Physical Room | 可被分配和占用的具体客房资源 | 房号通常门店内唯一，内部房间 ID 的作用域由数据模型确定 |
| TERM-11 | 住宿区间 / Stay Range | 按酒店当地日期表示的 `[入住日, 退房日)` | 不等同 UTC 时间戳区间；小时房等见 DEC-16 |
| TERM-12 | 房晚 / Room Night | 一间实体客房在一个住宿日期上的业务计量单位 | 一单两间房两晚对应四房晚，不等于四张订单 |
| TERM-13 | 预订订单 / Reservation | 客户申请或购买住宿的业务单据 | 不是房间占用记录，也不是支付交易 |
| TERM-14 | 房间占用 / Room Allocation | 订单或批准业务对某实体客房某区间的占用事实 | 必须保留归属与历史；不能只用房态显示表示 |
| TERM-15 | 临时锁房 / Hold | 到期前等待确认的临时有效占用 | “到期”不等于已经在事务中完成释放 |
| TERM-16 | 预订确认 / Confirmation | 满足规则后订单及占用进入确认状态的业务结果 | 不必然意味着在线支付完成；到店付与 OTA 代收需各自规则 |
| TERM-17 | 释放 / Release | 通过合法状态迁移解除相应未来资源占用的业务效果 | 不能根据重复消息直接增加计数，也不等于删除历史记录 |
| TERM-18 | 取消 / Cancellation | 终止未履约或允许取消部分的业务申请与结果 | 取消、退款、渠道确认可能异步完成，不能混成同一个状态 |
| TERM-19 | 未入住 / No-show | 满足批准条件后认定预订未按约入住 | 截止时间、收费及释放规则尚待 DEC-06 |
| TERM-20 | 排房 / Room Assignment | 将房型需求与实体房关联或依法调整关联 | 建议内部即时排房，真正未分房配额见 DEC-05 |
| TERM-21 | 入住记录 / Stay Record | 实际入住人、客房与履约过程的记录 | 不等同订单状态，支持程度受部分履约决定影响 |
| TERM-22 | 续住 / Stay Extension | 在当前住宿基础上增加获准区间 | 新增区间仍须竞争资源、核价并原子提交 |
| TERM-23 | 换房 / Room Change | 调整已安排或正在履约的房间关联 | 目标失败时原有效资源不得丢失；首期建议同店 |
| TERM-24 | 离店 / Check-out | 完成批准的入住终结及结算检查 | 不删除入住历史；清洁状态、占用结束和资金结清分别处理 |
| TERM-25 | 维修/停用区间 / Room Block | 因维修或运营原因禁止销售的资源区间 | 不能被占用表排斥约束自动覆盖；需统一互斥协议 |
| TERM-26 | 清洁状态 / Housekeeping Status | 待清洁、清洁中、待检查等客房运营状态 | 清洁完成不能释放预订；能否入住须结合业务规则 |
| TERM-27 | 房型可售量 / Sellable Availability | 根据合法占用、维修、政策等计算的销售视图 | 每晚有余房不保证存在整段可住的同一实体房 |
| TERM-28 | 未分房配额 / Unassigned Allotment | 尚未绑定实体房的销售预留模型 | 不是简单库存缓存；若启用需独立不变量、转换和释放协议 |

## 3. 价格、资金与报表

| 编号 | 中文 / 英文 | 本项目含义 | 必须区分 |
| --- | --- | --- | --- |
| TERM-29 | 价格计划 / Rate Plan | 房型、日期、限制与取消政策等构成的销售规则 | OTA 外部价格计划经映射后才能进入内部模型 |
| TERM-30 | 报价快照 / Quote Snapshot | 一次报价的金额、币种、政策、版本及有效性信息 | 后续改价不应覆盖已确认的成交记录 |
| TERM-31 | 账项 / Folio Entry | 房费、消费、收款、调整等可追溯账务记录 | 原账项错误以受控冲正/调整处理，不直接抹掉历史 |
| TERM-32 | 应收 / Receivable | 按业务及金额口径应当收取的金额 | 不等于已经收到的资金 |
| TERM-33 | 实收 / Received Funds | 经对应收款流程确认已收到的资金 | 手工现金记账不代表支付服务商已经确认交易 |
| TERM-34 | 押金 / Deposit | 按批准规则收取并可能退回或抵扣的款项 | 不直接等同营业收入；与支付预授权也不自动等同 |
| TERM-35 | 支付交易 / Payment Transaction | 与服务商或收款方式相关的独立资金过程 | 支付成功不自动证明房间仍可确认 |
| TERM-36 | 退款 / Refund | 对已收资金发起并核实退回的资金过程 | 申请受理、处理中、成功和失败应分开；不能超过可退额度 |
| TERM-37 | 冲正 / Reversal | 用关联记录纠正原账项的受控会计业务动作 | 本地冲正不自动触发外部真实退款 |
| TERM-38 | 营业日 / Business Date | 酒店用于经营归属和日结的业务日期 | 不一定等于服务器自然日；切换规则见 DEC-07 |
| TERM-39 | 夜审/日结 / Night Audit | 对指定营业日进行核对、结账或批准记账的批处理 | 重跑不重复入账；失败可恢复；内容由业务规则确定 |
| TERM-40 | 对账 / Reconciliation | 对订单、占用、流水或外部资金/渠道数据进行核对 | 差异发现不是修复成功；不能强改事实消除差异 |

## 4. 集成与可靠性

| 编号 | 中文 / 英文 | 本项目含义 | 必须区分 |
| --- | --- | --- | --- |
| TERM-41 | 幂等键 / Idempotency Key | 在明确作用域内标识同一次请求意图的键 | 不是只要字符串相同就跨租户复用结果；同键异内容应冲突 |
| TERM-42 | 操作 ID / Operation ID | 标识一次取消、释放、退款等业务操作 | 一次操作可产生多条房晚流水，行级去重键须另行设计 |
| TERM-43 | 外部订单号 / External Order ID | 渠道协议给出的订单标识 | 必须与实际渠道/账号/门店唯一作用域组合使用 |
| TERM-44 | Outbox | 随交易原子落库、等待可靠发布的事件记录 | 发布可重复，不能凭发送请求发出就认定对方已处理 |
| TERM-45 | Inbox | 与本地消费效果同事务落库的去重记录 | 不得先标已消费再异步执行业务 |
| TERM-46 | 未知结果 / Unknown Outcome | 因超时/断连无法判断操作是否成功 | 不等于失败；先按业务键查询再决定安全重试 |
| TERM-47 | 补偿 / Compensation | 在部分外部动作已发生后恢复可接受业务结果的动作 | 不等于数据库回滚，补偿自身也可能失败或需要重试 |
| TERM-48 | 审计 / Audit | 可追溯的身份、动作、对象、结果、时间和原因记录 | 普通应用日志不自动满足关键审计完整性与保护要求 |
| TERM-49 | 派生房态 / Inventory Projection | 从权威占用与运营记录计算的查询数据 | 可重建且可能延迟，不能成为绕过事实约束的写入权威 |
| TERM-50 | SLO / RPO / RTO | 服务目标、允许数据损失口径、恢复时间目标 | 都需要统计边界、故障域和验证证据；目标不是现状 |

## 5. 命名和使用规则

- 文档、API 和页面需要分别说清“订单状态”“占用状态”“入住状态”“支付状态”“清洁状态”，不统一称为一个“房态状态码”。
- “成功”须说明对应层次：请求已接收、本地已提交、渠道已确认、服务商已核实到账或人工处置已完成。
- “释放库存”须指明释放的占用或配额及一次性操作依据，不能表示无条件增加汇总数量。
- S0-02 确定最终状态枚举和联动规则后同步术语；术语冲突先更新定义与用例，再修改实现。

## 6. S0-02 候选对象和状态补充

[状态机设计](../domain/state-machines.md)新增了用于分析的房间级履约子项 L、入住会话 S 和实际房间分段 G。它们细化 TERM-13/14/21 的关系：主单包含房间级需求，实体占用记录负责防重，会话表示一次实际履约，分段保存换房前后的实际客房使用历史。物理表映射尚待 S0-04 决定。

`A.COMPLETED` 表示离店后的历史占用，`A.SUPERSEDED` 表示被后继版本替换；`O.PARTIALLY_*` 与 `O.CLOSED_MIXED` 是多房订单聚合候选，不应与某间房的实际状态混用。以上均是设计建议，不是已批准或已实现的枚举；其详细条件与待定分支以状态机文档为准。
