# 企业级酒店 PMS 技术架构设计文档

> 文档版本：1.0\
> 状态：架构设计基线（待业务、容量与渠道准入信息确认）\
> 目标场景：大型酒店集团、多租户 SaaS、实体客房级库存、目标规模 500
> 家以上门店、初期由单人结合 AI 编程开发\
> 核心目标：防止重复锁房与超卖；确保订单幂等；支持 OTA
> 可恢复同步；具备可验证的高可用、安全和灾难恢复能力。

------------------------------------------------------------------------

## 1. 文档目标与设计原则

本文定义酒店 PMS（Property Management
System）的目标架构、关键领域模型、库存一致性机制、OTA
幂等协议、部署与运维基线，以及分阶段研发路线。

本系统应覆盖：

-   集团管理端：集团组织、门店、用户权限、经营分析、配置和审计。
-   酒店商家端：房态日历、房型与房间、订单、价格、账务、渠道管理。
-   前台操作端：预订、排房、入住、续住、换房、离店、维修房和清洁状态。
-   用户端：H5、微信小程序等自有预订入口。
-   OTA 集成：美团、携程、抖音及后续获授权的平台。
-   可靠性能力：幂等、事务、消息重试、对账补偿、备份恢复、监控告警和安全审计。

### 1.1 设计原则

1.  **数据正确性优先**：订单、客房占用和库存变更必须有可验证的一致性约束。
2.  **数据库是交易事实源**：Redis、消息队列和前端状态都不能作为最终库存权威。
3.  **默认假设请求和消息会重复**：所有外部请求、事件消费、取消与释放操作都要设计幂等。
4.  **核心交易保持短事务**：数据库事务中不调用 OTA、支付或其他外部 HTTP
    服务。
5.  **模块化单体优先**：先通过模块边界降低耦合，只有在有容量或隔离需求时才拆服务。
6.  **故障可恢复**：对超时、进程崩溃、数据库切换、重复回调和消息积压设计恢复路径。
7.  **依赖少而受控**：固定版本、自动化测试、版本化数据库迁移和可回滚发布。
8.  **安全默认开启**：租户隔离、最小权限、密钥保护、敏感信息最小化和审计从第一版建立。
9.  **目标可测量**：所有
    SLA、RPO、RTO、吞吐和延迟目标均需通过测试与生产监控验证。
10. **渠道解耦**：外部 OTA 数据结构不能直接成为核心领域模型。

### 1.2 非目标

首期不默认采用以下方案：

-   为了"微服务化"而把订单、库存、房态、账务拆成大量独立服务。
-   让 Redis 分布式锁单独承担防止重复占房的职责。
-   直接采用跨地域多主写入处理同一实体房间的预订。
-   在尚无性能证据时引入
    Kubernetes、服务网格、分布式数据库分片或复杂流处理平台。
-   把"恰好一次消息投递"当成正确性前提。
-   承诺未经压测、故障演练和正式运维流程验证的可用性指标。

## 2. 可靠性目标与验收口径

"最高标准"必须转化为明确、可测量的目标。以下为建议目标，不代表系统当前已经达到。

  -------------------------------------------------------------------------------------------------------
  指标                     建议目标                验收要求
  ------------------------ ----------------------- ------------------------------------------------------
  核心交易可用性           99.99%                  明确统计窗口、维护窗口和依赖故障归属；用监控数据验证

  已确认订单 RPO           0                       对已向调用方确认成功的交易，按规定故障模型不得丢失

  核心服务故障 RTO         ≤ 5 分钟                通过定期故障切换演练验证

  单实体客房重复有效占用   0                       并发测试与数据库约束验证

  同一 OTA 订单重复创建    0                       重复请求、超时重试和重复回调测试

  库存释放重复执行         0                       状态机与库存流水验证

  关键审计事件完整性       100% 记录               对订单、库存、权限、账务等关键变更做审计核对

  备份恢复                 定期演练                恢复到隔离环境，核验数据完整性和可用性

  性能指标                 待压测确定              依据订单峰值、门店数、查询模式和 SLO 制定
  -------------------------------------------------------------------------------------------------------

### 2.1 RPO=0 的前提

RPO=0
不能仅靠每日备份或异步复制保证。需要定义故障模型，并采用合适的同步持久化策略、可靠的故障仲裁和旧主库隔离机制。跨可用区同步复制会增加写入延迟；跨地域同步复制可能明显影响交易延迟与可用性。

### 2.2 99.99% 的含义

99.99% 年度可用性对应约 52.6
分钟/年的不可用预算。必须明确可用性统计的是整个预订交易链路还是单一
API，计划维护是否计入，以及 OTA 等外部平台故障是否计入系统自身 SLA。

### 2.3 容量目标

"500 家门店"不能直接推导出服务器规格。容量模型至少需要：

-   高峰订单创建速率（笔/秒）。
-   房态日历读取速率和查询时间范围。
-   同一热门酒店/房型的热点程度。
-   OTA 回调峰值、重试比例和渠道数量。
-   每笔订单涉及的房间数与入住晚数。
-   报表查询负载、保留年限和审计日志增长量。
-   可接受的 p95 / p99 延迟。

在容量数据确认前，不给出未经验证的固定服务器规格。

### 3.3 模块化单体的模块边界

建议一个代码仓库，按业务模块分包，避免形成无法治理的"大杂烩"：

-   `identity`：登录、认证、会话、权限。
-   `tenant`：租户、集团、门店和组织关系。
-   `room`：房型、实体房间、维修与清洁状态。
-   `reservation`：预订、订单状态机、占用记录。
-   `inventory`：房型库存视图、房间可售计算、库存流水。
-   `pricing`：价格日历、价规、渠道价格映射。
-   `frontdesk`：入住、离店、续住、换房。
-   `payment`：支付、退款、对账；遵循支付服务商的接口协议。
-   `channel`：渠道配置、外部 ID 映射、适配器接口。
-   `integration`：Inbox、Outbox、重试与补偿任务。
-   `audit`：关键操作审计。
-   `reporting`：经营报表与异步导出。

模块之间通过明确的服务接口和领域事件交互。首期不需要把每个模块都拆成独立部署服务。

## 4. 核心领域模型与数据表设计

### 4.1 关键领域概念

必须分开建模：

1.  **预订订单**：客户购买或申请的业务单据。
2.  **房间占用**：具体实体房间在某个入住日期区间内被某笔业务占用。
3.  **客房运营状态**：清洁中、待检查、维修、停用等。
4.  **房型库存**：某房型在某日可售的数量或配额，是汇总/销售层概念。
5.  **入住记录**：实际入住人与房间的关联。
6.  **账务记录**：收款、退款、押金、消费及结算。
7.  **渠道订单映射**：本地订单与 OTA 外部订单标识的关联。

不要用一个 `room_status`
字段同时表示预订占用、清洁状态、维修状态和入住状态。

### 4.2 建议的核心表

  ---------------------------------------------------------------------------------------------------------------------------------
  表                      关键字段                                                                     约束与用途
  ----------------------- ---------------------------------------------------------------------------- ----------------------------
  `tenant`                `id`、`tenant_code`、`status`                                                租户根对象

  `hotel_group`           `id`、`tenant_id`、`name`                                                    集团组织

  `hotel`                 `id`、`tenant_id`、`group_id`、`timezone`                                    门店、时区与归属

  `room_type`             `id`、`hotel_id`、`code`、`capacity`                                         房型定义

  `physical_room`         `id`、`tenant_id`、`hotel_id`、`room_type_id`、`room_no`                     实体房间

  `room_block`            `id`、`room_id`、`stay_range`、`reason`、`status`                            维修、停用等不可售区间

  `reservation`           `id`、`tenant_id`、`hotel_id`、`status`、`version`                           预订主单与乐观版本

  `reservation_room`      `id`、`reservation_id`、`room_id`、`stay_range`、`status`                    房间级占用记录

  `ota_order_mapping`     `channel_id`、`external_order_id`、`reservation_id`                          渠道订单映射

  `inbox_event`           `consumer_name`、`event_id`、`processed_at`                                  消费去重

  `outbox_event`          `event_id`、`aggregate_id`、`aggregate_version`、`payload`、`published_at`   可靠事件发布

  `payment_transaction`   `payment_id`、`reservation_id`、`provider_ref`、`status`                     支付交易记录

  `audit_log`             `actor_id`、`tenant_id`、`action`、`target_id`、`created_at`                 审计留痕

建议为主要业务表设计 `created_at`、`updated_at`、必要的
`version`、外键和唯一约束。并非所有表都必须重复保存
`tenant_id`；若为查询性能和隔离而冗余保存，必须通过约束或事务逻辑确保租户归属一致。

### 4.3 日期区间约定

全系统统一使用入住日期包含、退房日期不包含的半开区间：

-   入住：2026-10-20
-   退房：2026-10-22
-   占用范围：`[2026-10-20, 2026-10-22)`

这样 10 月 22
日可作为下一笔预订的入住日期。清洁缓冲、延迟退房和提前入住应通过独立规则或运营状态建模，不能随意改变日期区间语义。

### 4.4 实体房间的数据库防重

PostgreSQL
的日期范围与排斥约束可作为防止重叠占房的数据库级最后防线。以下为概念性
DDL，正式迁移前需要验证版本、权限、索引扩展、外键和业务状态定义。

``` sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE reservation_room (
    id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id       BIGINT NOT NULL,
    hotel_id        BIGINT NOT NULL,
    room_id         BIGINT NOT NULL,
    reservation_id  BIGINT NOT NULL,
    stay_range      DATERANGE NOT NULL,
    status          VARCHAR(24) NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT valid_stay_range
        CHECK (NOT isempty(stay_range)),

    CONSTRAINT no_overlapping_active_room_bookings
        EXCLUDE USING gist (
            room_id WITH =,
            stay_range WITH &&
        )
        WHERE (status IN ('HELD', 'CONFIRMED', 'CHECKED_IN'))
);
```

实施注意事项：

-   `HELD`、`CONFIRMED`、`CHECKED_IN` 等状态集合必须与正式状态机一致。
-   `room_id` 应通过外键关联实体客房；应用或数据库层还需确保
    `tenant_id`、`hotel_id` 与该房间的归属一致。
-   过期锁房不能只靠时间戳自动退出排斥约束；清理任务必须在事务中检查状态并合法转为
    `EXPIRED` 或 `RELEASED`。
-   多房间预订的全部占用应在一个事务内写入；任一房间冲突时整体回滚。
-   数据库排斥约束解决实体房间区间冲突，不自动解决支付状态、OTA
    确认、维修状态或房型销售配额问题。

### 4.5 房型库存与实体占用

建议以 `reservation_room`
作为实体房间占用的权威事实记录，房型日历和房态查询数据作为可重建的派生数据。

如果需要 OTA
提前销售尚未分配具体房号的房型库存，应额外设计房型级配额/预留机制，并规定预售配额、实体分配和超售策略之间的严格关系。不能仅从"实体房间当前未分配"推断其一定可售，因为它可能被维修、集团配额或其他销售策略占用。

## 5. 锁房与订单状态机

### 5.1 建议状态

临时锁房和订单状态最好分开建模。示例锁房状态：

-   `HELD`：临时占用，尚未最终确认。
-   `CONFIRMED`：预订确认，占用持续有效。
-   `RELEASED`：主动取消或其他合法流程释放。
-   `EXPIRED`：临时占用超时并已完成释放。
-   `CHECKED_IN`：已办理入住，仍然占用房间。

订单状态可另行定义，例如
`PENDING`、`CONFIRMED`、`CANCELLED`、`CHECKED_IN`、`CHECKED_OUT`、`NO_SHOW`，并对合法迁移进行约束。不要让所有状态混在一个枚举中。

### 5.2 锁房事务

典型的房间锁定流程：

1.  校验身份、租户、门店、房间与日期区间。
2.  在数据库事务内写入幂等记录或锁定已有幂等记录。
3.  检查业务规则与房间运营状态。
4.  插入 `reservation_room` 占用记录，让数据库排斥约束裁决并发冲突。
5.  创建或更新订单。
6.  写入库存流水。
7.  写入 Outbox 事件。
8.  提交事务。
9.  事务提交成功后再返回成功结果。

若插入占用记录时发生排斥约束冲突，整个事务回滚，并按业务规则返回房间不可用。不能先向用户报告锁房成功，再异步补写数据库。

### 5.3 超时释放

超时任务应采用可重复执行的事务化流程：

1.  查询一批已过期且状态仍为 `HELD` 的记录。
2.  通过行锁或条件更新竞争领取任务。
3.  再次检查状态与到期时间。
4.  将记录从 `HELD` 迁移为 `EXPIRED`。
5.  写入一次性库存释放流水和必要的 Outbox 事件。
6.  提交事务。

状态迁移与释放流水必须原子提交。可使用条件更新、唯一操作 ID
和数据库约束避免重复释放。不能仅根据过期时间直接增加可售数量。

### 5.4 事务与锁顺序

为降低死锁风险：

-   统一多房间/多日期锁定时的资源排序，例如按
    `hotel_id`、`room_id`、`stay_date` 排序。
-   保持事务短小，避免事务中调用外部 HTTP 服务。
-   对可安全重试的死锁或序列化失败设置有限次数的退避重试。
-   对不可判定的提交结果，先根据幂等键和业务记录查询结果，不得直接重放非幂等操作。
-   记录锁等待时间、死锁次数和事务持续时间，设置告警阈值。

## 6. OTA 幂等与可靠集成

### 6.1 统一接入协议

每个 OTA 适配器负责：

-   签名、来源、时间戳和重放保护。
-   外部字段与内部领域模型映射。
-   外部订单号、房型 ID、价格计划和状态码映射。
-   渠道特定的响应时限与确认语义。
-   限流、重试、错误分类和对账。
-   版本兼容、凭证轮换和渠道健康度监测。

核心订单服务不得直接依赖某个 OTA 的专有 SDK 或字段结构。

### 6.2 三类唯一标识

  ----------------------------------------------------------------------------
  标识                                典型作用
  ----------------------------------- ----------------------------------------
  `channel_id + external_order_id`    同一渠道订单只能映射到一个本地订单

  `channel_id + request_id`           防止同一请求重复执行
  或渠道协议认可的幂等键              

  `operation_id`                      防止取消、释放、退款等业务操作重复执行
  ----------------------------------------------------------------------------

同一幂等键但请求内容不同，应拒绝覆盖原请求并记录安全/协议异常。同一外部订单号但请求
ID
不同，应按渠道协议识别为订单更新、取消或重复通知，不能直接创建新订单。

### 6.3 Inbox / Outbox

-   订单、库存占用、库存流水和 Outbox 事件应在同一数据库事务中提交。
-   Outbox 发布器可重复发送事件；发布成功后更新发布状态。
-   消费者将 Inbox 去重记录与本地业务变更放入同一事务。
-   对外部 HTTP
    调用不能假设与数据库事务原子提交，应设计调用状态、重试、查询确认和补偿流程。
-   事件携带
    `event_id`、`aggregate_id`、`aggregate_version`、`event_type`
    和创建时间。
-   过期或乱序事件应根据版本与状态机判断，不得覆盖更晚的业务状态。

### 6.4 OTA 异常处理矩阵

  场景                   处理方式
  ---------------------- --------------------------------------
  重复订单推送           唯一约束与幂等记录返回原结果
  本地已提交但响应丢失   重试时查询原交易，不创建第二笔
  取消通知重复           状态机与唯一释放操作确保只释放一次
  OTA 调用超时           记录不确定状态，按渠道协议查询或重试
  库存推送失败           Outbox 持久化、退避重试、告警
  回调乱序               检查聚合版本与合法状态迁移
  渠道不可用             隔离渠道故障，保留任务并监控积压
  本地与渠道状态不一致   周期性对账、生成差异任务、可审计补偿

"恰好一次投递"不应作为前提。应假设消息至少一次投递，并通过幂等消费、状态机和对账补偿实现业务正确性。

### 6.5 渠道准入风险

技术上完成适配器并不代表一定获得 OTA
直连接入资格。美团、携程、抖音等平台的商务合作、供应商准入、接口授权、测试环境和上线验收流程应逐一确认。项目计划应为渠道申请和联调预留不确定性，不应把未经确认的接口可用性当成已完成依赖。

## 7. 多租户、安全与隐私

### 7.1 多租户模型

建议按以下层级组织：

-   租户（签约经营主体）。
-   酒店集团（可选组织层级）。
-   门店。
-   业务数据。
-   用户、角色和数据范围。

所有查询和写入都必须经过服务端授权。不得信任客户端传来的 `tenant_id` 或
`hotel_id`。对高风险操作应校验用户对目标门店和业务对象的实际权限。

PostgreSQL RLS
可作为额外防线，但必须验证连接池上下文、数据库角色、表所有者和绕过策略。RLS
不应替代应用层授权。

### 7.2 安全基线

-   后台使用 RBAC，并将角色权限与门店数据范围分开。
-   数据库应用账号遵循最小权限原则，禁止业务连接使用超级用户。
-   OTA 密钥、支付密钥和签名凭证不得进入代码库、镜像或普通日志。
-   对身份证件、手机号等个人信息实施最小化收集、加密存储、脱敏展示和访问审计。
-   支付回调必须验签、校验金额和业务单号，并具备幂等处理。
-   API
    实施身份认证、权限检查、限流、输入校验、请求体限制和必要的防重放控制。
-   依赖漏洞扫描、软件物料清单（SBOM）、镜像扫描和补丁流程纳入发布管线。
-   关键审计记录应具备防篡改、访问控制、保留策略和异常告警。
-   开发、测试、预发布和生产环境分离，禁止使用真实生产个人数据做开发测试。
-   密钥轮换、员工离职权限回收和应急凭证轮换必须形成操作流程。

## 8. 高可用、灾备与部署

### 8.1 目标部署形态

``` text
DNS / WAF / Load Balancer
            |
       多个 API 实例
            |
  ---------------------------
  |                         |
PMS 模块化应用          OTA Worker
  |                         |
  -------- PostgreSQL -------
              |
      同步/受控复制与仲裁
              |
      独立异地备份与归档
```

### 8.2 部署要求

1.  应用实例尽可能无状态化，可水平扩展。
2.  核心数据库使用受支持的高可用方案，明确主备角色、复制模式、仲裁、旧主隔离和切换流程。
3.  需要 RPO=0
    时，必须针对规定的故障范围验证同步持久化行为；不要把异步副本误认为零数据丢失保障。
4.  备份应与生产故障域隔离，具备加密、访问控制和定期恢复演练。
5.  数据库、消息队列、应用与监控的故障告警应有明确的处理责任和升级路径。
6.  发布应支持版本化迁移、灰度或分批发布、健康检查和回滚；数据库迁移需特别考虑新旧应用版本兼容。
7.  生产数据库不要仅依赖容器自动重启或单机 Docker Compose 来实现高可用。
8.  初期可以用 Docker Compose 管理应用与 Worker；是否引入 Kubernetes
    应由团队运维能力、发布需求和实际规模决定。

### 8.3 灾备演练

至少覆盖：

-   应用实例突然退出。
-   OTA Worker 在事务提交前后退出。
-   数据库主节点不可用。
-   主备切换期间客户端连接中断。
-   网络分区和旧主隔离。
-   误删数据后的时间点恢复。
-   备份文件损坏或无法恢复。
-   消息队列积压与重复投递。
-   密钥泄露后的轮换和权限收敛。

每次演练记录故障发现时间、恢复时间、数据核对结果、RPO/RTO 和未解决问题。

### 8.4 观测指标

核心指标至少包括：

-   API 成功率、p95/p99 延迟、超时和限流次数。
-   订单创建成功/失败数量及失败原因。
-   房间占用冲突、数据库排斥约束冲突、死锁和锁等待。
-   临时锁房数量、超时待清理数量、释放失败数量。
-   Outbox 未发布数量、最老事件年龄、Inbox 重复事件数量。
-   OTA 每渠道成功率、超时率、重试量、限流量和积压量。
-   数据库连接池使用率、事务时长、复制延迟和存储增长。
-   备份成功率、最近一次恢复演练时间及验证结果。
-   权限拒绝、异常登录、敏感数据访问和高风险操作。

## 9. 测试策略与上线门槛

### 9.1 必测场景

  测试                         验收条件
  ---------------------------- ----------------------------------------
  同一房间、相同日期并发抢订   不存在重叠有效占用
  同一 OTA 订单重复推送        不重复创建订单或占用
  事务提交成功但响应丢失       重试返回原处理结果
  取消与确认并发               最终状态符合状态机，库存只释放一次
  多房间订单部分冲突           整体回滚，无部分占用
  多晚订单部分日期冲突         整体回滚，无部分日期占用
  Outbox 发布时进程崩溃        恢复后事件仍可发送
  OTA 回调重复和乱序           不覆盖新状态、不重复扣减库存
  数据库主备切换               按目标验证数据一致性与恢复时间
  跨租户访问测试               无越权读取或修改
  库存流水核对                 占用记录、释放记录和派生库存可交叉核验
  依赖与安全测试               关键漏洞、权限配置和密钥泄露检查通过

### 9.2 并发测试原则

-   使用真实 PostgreSQL 测试环境，而不是只使用内存数据库。
-   使用固定随机种子或保存测试输入，保证问题可复现。
-   并发测试不仅检查 HTTP
    响应，还检查数据库占用记录、订单、库存流水和幂等记录。
-   测试进程崩溃、事务回滚、数据库连接断开、超时和重试。
-   在热门酒店、热门房间和相同入住日期上模拟热点竞争。
-   负载测试应逐步增加并发，记录吞吐、p95/p99、锁等待、死锁、数据库 CPU
    与 I/O。
-   任何性能结果都要记录测试环境、数据规模、配置和测试脚本，不将实验室结果直接当成生产承诺。

### 9.3 上线门槛

在以下条件满足前，不应将系统视为已达到企业级生产标准：

-   核心状态机和数据库约束通过代码审查。
-   幂等、并发、故障注入和跨租户安全测试通过。
-   备份恢复和数据库故障切换演练通过。
-   OTA 渠道授权、接口协议、测试环境和上线验收已确认。
-   关键告警有负责人和处理流程。
-   生产发布、回滚、数据库迁移和密钥轮换流程经过演练。
-   SLA、RPO、RTO 与性能 SLO 有明确的测试报告和监控依据。

退出条件：渠道联调、重复通知、回调乱序和对账测试通过。

实现：

-   容量压测与数据库调优。

-   安全审计、依赖扫描和上线流程。

## 12. 必须记录的架构决策（ADR）

建议将以下决策写入 `docs/adr/`，避免后续开发过程中反复改变核心规则：

1.  **ADR-001：实体房间占用是权威事实，房型日历为派生数据。**
2.  **ADR-002：数据库约束是防止重复有效占房的最后防线。**
3.  **ADR-003：订单、占用、库存流水与 Outbox 在同一事务内提交。**
4.  **ADR-004：所有 OTA 订单和业务操作都具备持久化幂等语义。**
5.  **ADR-005：核心交易采用模块化单体，按证据决定是否拆服务。**
6.  **ADR-006：Redis 不作为最终库存权威，也不单独保证防超卖。**
7.  **ADR-007：核心交易的 RPO/RTO 与故障域必须明确，并通过演练验证。**
8.  **ADR-008：租户隔离和敏感数据保护属于基础架构要求，不作为后期补丁。**
9.  **ADR-009：所有数据库变更通过版本化迁移和回归测试。**
10. **ADR-010：OTA
    渠道准入与技术实现分开管理，未获授权的渠道不得宣称已接通。**

## 15. 最终设计约束

本系统应遵守以下不可绕过的核心约束：

-   任何成功的房间占用都必须有数据库提交作为依据。
-   同一实体房间在互斥日期区间内不得存在两笔有效占用。
-   多房间、多晚预订必须具备整体成功或整体失败的原子语义。
-   订单、房间占用、库存流水与待发布事件必须保持事务一致。
-   重复 OTA 请求、消息、取消和释放操作不得重复改变业务结果。
-   对不确定的网络结果先核实状态，不盲目重放非幂等操作。
-   所有高可用、零数据丢失和恢复时间目标都必须由真实故障演练验证。
-   系统的安全、可维护性与渠道准入不能只靠技术框架保证。

**实施优先级：先完成数据库约束、订单状态机、锁房事务和幂等协议，再扩展多端
UI 与 OTA 渠道数量。**
