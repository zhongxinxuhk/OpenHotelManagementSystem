# 平台业务管理端（platform-ops）

> 身份平面：**PLATFORM**（跨租户）。
> 状态：**BLOCKED** — 依赖 DEC-01（租户/集团/加盟主体划分）与 DEC-02（跨主体可见范围与支持访问授权）。

## 定位

平台雇员的日常工作台，服务对象是**租户，不是客人**：

| 角色 | 日常动作 |
| --- | --- |
| 客服 | 查租户与门店、看某订单为何失败、按工单联系商家 |
| 售后 | 处理商家投诉、退款争议的**申请与流转**（钱从哪出由 DEC-08 决定） |
| 运营 | 看各租户的开通情况与活跃度、推开通、配置话术与公告 |

## 为什么现在不能做

平台雇员要"跨租户看数据"，而当前系统里**不存在跨租户的合法身份**：

- `app_user` 带 `tenant_id`，所有查询强制租户过滤（ADR-016）；
- 平台账号塞进某个租户 → 看不到别家；
- 给 `app_user.tenant_id` 加可空 → 所有租户过滤出现一个可空分支，
  隔离从"编译期保证"退化成"每个查询记得写空分支"。

因此本端必须先有 `PLATFORM` 平面的身份表与会话（A-05 / A-07），
而这条平面的边界**正是 DEC-01/DEC-02 要回答的问题**：

1. 平台是"运营方"还是"各主体各自代管"？
2. 支持访问（support access）是"经批准、限时、留痕"的临时授权，还是常驻权限？
3. 平台雇员能看到别的租户的业务数据到什么粒度？实名信息能否看到？

**在 DEC-02 定案前不得实现，也不得写"先给个超管角色跑起来"的临时方案**——
那会变成事实上的跨租户后门，而且是最难回收的那种（一旦有人用惯了就删不掉）。

## 技术栈（定案后）

Ant Design Pro 6，与 `merchant-web` 同范式但**独立部署、独立域名**：
客服能看到跨租户工单，这个产物绝不能和商家端打成同一个 bundle。

## 一旦 DEC 定案，第一步做什么

1. 迁移：`platform_user` 表（不带 `tenant_id`）+ `platform_session` + 平台动作清单
   （**不复用**租户内的 `role`/`permission`：平台动作与业务动作语义不同）；
2. 支持会话：`support_grant`（谁批准、给谁、哪个租户、有效期、用途），到期自动失效；
3. 所有平台侧读写强制写审计（B-05 目前也只有一半）。
